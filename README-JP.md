## KataHana とは

KataHana は、囲碁を「打つ」ためと、打ち終わった対局を「検討する」ためのクライアントです。Compose Multiplatform で書かれているため、ゲームロジックと UI の大部分はひとつの共有モジュールに集約され、デスクトップ（JVM）版と Android 版がそれを共用します。リポジトリには iOS アプリのシェルも含まれています。棋譜はあなたのものです。盤もルールも棋譜ツリーも保存した対局もすべて端末上にあり、登録すべきアカウントも、あなたの棋譜を預かるクラウドサービスもありません。その一方で、このアプリは局面を「判断する」エンジンに依存しています。クライアントは棋力と評価の面で意図的に無知であり、AI 対戦相手・勝率・目数グラフ・領地オーバーレイ・棋譜全体の検討はすべて、WebSocket 越しに話しかける KataGo 互換プロセスから得られます。そのプロセスは通常、このリポジトリ同梱のゲートウェイをデスクトップ PC 上で動かしたものです（スマホは同じネットワークからそのアドレスを指します）。ただし、同じプロトコルで話せる相手なら、どのマシンでも構いません。エンジンに到達できない間も、対人対局・棋譜ツリー・保存はすべて機能しますが、判断を伴う機能は空のままです。つまり、使えてはいるものの、明らかに機能を欠いた状態になります。

このプロジェクトが存在するのは、囲碁ソフトウェアにありがちなトレードオフのせいです。多くのツールは、オンラインの対局サービスか、ローカルに導入済みのエンジンか——どちらか一方を前提としています。どちらの前提にもコストがあります。サーバーは棋譜を他人のプラットフォームに預けることになり、接続なしでは使えません。エンジンは逆に、特定のハードウェア向けにバンドル・設定されるのがふつうで、これは KataGo にとっては深刻な問題です。KataGo のバイナリは GPU ごとに異なり、単一のインストール可能なファイルとして配布できないからです。KataHana はどちらの前提も避けようとしています。棋譜データはあなたのものであり、エンジンは、アプリが必要なときだけ通信する外部プロセス（通常は自分のマシンかネットワーク上のゲートウェイ）にすぎません。結果として、対人対局は常に動作し、AI 対応は前提ではなく追加機能になります。

アプリの残りの部分は、次の 3 つの決定から導かれます。以降の節で説明する機能のほとんどは、その帰結です。

- **ルールはアプリ自身が実装している。** KataHana は囲碁のルールをローカルで執行します。自殺手は拒否され、positional superko によって全局同形の再現は退けられ、連続 2 回のパスで対局は終了します。つまり、エンジンを何も繋げなくても対局は最初から最後まで成立し、エンジンには評価と着手選択という、本来得意な仕事だけが頼まれます。
- **エンジンは依存関係ではなくサービスとして扱う。** クライアントは素の WebSocket で KataGo 互換のプロセスに接続し、KataGo 自身の Analysis JSON をフレーム単位でやり取りします。勝率は一貫して黒番基準で扱われるため、対局の途中で数値の意味が変わることがありません。接続は任意なので、エンジンに依存する UI の部分は、エンジンがいない間は空のまま静かにしています。
- **AI の対戦相手は「色ごとのシート（席）」であり、強さを選べるものであって、固定設定ではない。** 各色は独立して人間・段位 AI・人間らしい AI・KataGo 9D+ のいずれかに設定でき、対局の途中で変更もできます。とりわけ、エンジンは常に全力で打つよう求められるわけではありません。人間らしい AI と段位 AI は、15k〜3d（15 級〜3 段）の間で選んだ棋力に合わせてエンジンの policy 出力から着手を引くため、その棋力らしい、人間として納得できる負け方をします。だからこそ、弱い相手との練習にも使えるのです。
- **棋譜ツリーが検討のモデルである。** すべての着手は分岐するツリーのノードであり、Undo と Redo はそのツリーを歩くことです。過去の局面から打てば変化が生まれます。エンジンが手を下すのは常にツリーの葉の上、自分の色の番だけなので、脇道を検討している最中に AI が突然「応答」してくることはありません。

この文書の残りは、実際に触れる順番に沿ってアプリを説明します。まずホーム画面、次に盤面と対局の流れ、その次に解析と検討の機能、最後にエンジン接続・外観設定・ビルド手順です。

## 主な機能

以下のリストは、実際に使ってみて目立つ点の要約です。それぞれについては、以降の節で詳しく説明します。

- **盤優先のレイアウト。** 盤は画面の最大の要素であり、補助的な操作は必要なときまで脇に控えます。パス・Undo・Redo は盤のそば——縦向きなら上部の細いバー、横向きのスマホならレール——に置かれ、勝率は細いバー 1 本で示されます。保存・候補手・棋譜ツリー・オーバーレイのトグルは、ピンクの小さなタブから開くドロワーにまとめられています。広いウィンドウでは、その一部が盤の横の常設カラムに表示されます。
- **縦軸に意味がある形勢グラフ。** 目数差と勝率をひとつのグラフで扱い、小さなセレクタで 2 つのモードを切り替えます。勝率モードでは軸が固定され、黒 100% が上端、白 100% が下端、50% が中央に来ます。つまり、表示された値は解読が必要なオフセットではなく、縦の位置にそのまま対応します。線の色はリードしている方に傾き、最新のサンプルには小さなライブの数値ラベルが付き、グラフ上のどこかをクリックすると棋譜ツリーがその手まで移動します。
- **最善手を物差しにした着手品質。** 各着手はエンジンが見つけた最善手と比較され、失った目数が等級を決めます。しきい値は KaTrain のデフォルト（12・6・3・1.5・0.5 目）で、設定画面から変更できます。各色の最近の着手には等級が小さな顔として盤上に描かれ、盤の下の表には黒・白それぞれの等級の出現回数が集計されます。
- **石の下に描く連絡線。** 任意表示の連絡レイヤーは、囲碁を打つ人が実際に名前で呼ぶ 4 つの連絡——立・尖・飛・跳——を描きます。線は石の下に描画されるため、石を覆ったり、取られた石の上に乗ったりすることは決してありません。
- **塗り直しではなくオーバーレイとしての領地。** KataGo が返す領地マップは独立したレイヤーとして描かれるので、石とその色は常にはっきり見えます。新しいマップは、いきなり入れ替わるのではなく前のマップからクロスフェードし、レイヤー全体をオフにすることもできます。
- **ツリーに基づく検討モデル。** 最新の着手より前まで Undo すると検討モードに入ります。AI は葉で待機し、途中のノードから石を打てば、対局はそこから変化として分岐します。Redo は好みのラインを進み、エンジンが葉ではない局面に手を出すことはありません。合法点の長押しまたは右クリックで、エンジンの最善進行を仮想石としてプレビューできます。ツリーに新しい変化は作られません。
- **再起動しても残る対局。** 保存すると、対局は手ごとの評価とともに最近のリストに置かれます。そのため、開き直せば局面も形勢カーブも品質集計も戻ってきます。未保存の手を残したまま対局を抜けようとすると、アプリが先に保存するかどうかを尋ねます。棋譜をほかのツールに渡す必要があるときは、素の SGF（FF[4]）書き出しもあります。

これらの機能はすべて、13路盤の上で同時に見られます。石の下に連絡線が休み、新しい着手に表情が付き、最新の石にはリングがかかります。

## ホーム

アプリを開くとまずホーム画面が出ます。柔らかな暗い背景の上に、2 枚のカードが並んでいます。1 枚目は最近の対局リストです。各行には対局のタイトルと、盤サイズ・手数・対戦者をまとめた 1 行の要約が表示され、その行の背後には保存された対局全体が眠っています。したがって、項目を開けば、保存したときの局面・棋譜ツリー・形勢カーブが復元されます。候補手や領地マップのようなライブ情報は保存されていないため、盤面に戻ったときにエンジンへ改めてリクエストされます。

<p align="center">
  <img src="screenshots/home.jpg" alt="ホーム——最近の対局、git タグから生成された更新ログ、直近タグを読んだバージョン表記"/>
</p>

2 枚目は **What's new** で、プロジェクト自身の git 履歴から生成される更新ログです。タグ付きコミットには色付きのチップが付き、手書きの行はひとつもありません。リストはビルド時に `git log` から生成され、隅のバージョン表記は直近の git タグから取られます（現在のツリーでは `v1.6.5`、タグがひとつもない場合は `v0.1-alpha`）。この仕組みはコード構成の節でも触れます。というのも、これはアプリの中ではなく Gradle ビルドに実装されているからです。

## 領地（Ownership）

領地オーバーレイは、KataGo が解析と一緒に返す領地マップを使います。対局中のドロワーからオンにでき、マップは着手のたびに変わるため、新しいマップは急に入れ替わるのではなく、前のマップから短いクロスフェードで移り変わります。もとになるデータは常に同じで、変わるのは描画方法だけです。スタイルは次の 3 種類から選べます。

| ブロック | 霧 | 星座 |
|:---:|:---:|:---:|
| 1 点ごとの角丸タイル | 盤の上で混ざり合う連続的な霧 | かすかな顔と結ぶ線を持つ星 |
| <img src="screenshots/ownerships_1.png" alt="領地スタイル「ブロック」——黒白の勢力で染まる角丸タイル"/> | <img src="screenshots/ownerships_2.png" alt="領地スタイル「霧」——盤を覆う連続的なピンクと青の霧"/> | <img src="screenshots/ownerships_3.png" alt="領地スタイル「星座」——ほのかな顔と結ぶ辺を持つ星空"/> |

3 スタイルとも、待機中のアニメーションは意図的に控えめです。ブロックはわずかに弾み、霧は漂い、星座は呼吸して瞬きます。レイヤーは半透明を保つので、下の石は読みやすいままです。ここで重要な区別があります。**死石（Dead stones）**トグルはスタイルではなく、独立した機能です。オンにすると、KataGo が死に石と判断した石がその場で薄くなり、淡い黄色の光輪で縁取られます。石をひとつも盤から動かさずに終局の姿を確認できるわけです。このマーキングには、現在の局面のライブ領地評価が必要です。死に石の判定は領地マップから読み取られるからです。

## 対局

新しい対局は、実際の碁盤の前で決めるのと同じ質問から始まります。盤のサイズ、コミ、そしてそれぞれの色に誰が座るかです。対応する盤は 9路・13路・19路。コミは 6.5・7.5・0 から選べ、デフォルトは 7.5。ルールは positional superko 付きの中国ルールで、座標は GTP 座標——つまり文字の I は飛ばされます。新規対局シートは直前の選択も覚えているので、似た対局を始めるのは 1 タップですむことが多いです。

<p align="center">
  <img src="screenshots/p5.png" alt="新規対局シート——盤サイズ、コミ、人 vs AI、段位スライダー"/>
</p>

対局が始まると、盤がウィンドウの中央を占め、ほかの要素はすべてその周りに配置されます。縦向きのレイアウトでは、上部の細いバーにエンジンステータス・勝率バー・パス/Undo/Redo が並び、横向きでは右、縦向きでは下から開くドロワー（ピンクのタブかスワイプで開く）に残りが入ります。手番と取った石、候補手、棋譜ツリー、形勢グラフ、品質表、そして表情・連絡線・座標・領地・死石のトグルです。広いウィンドウと横向きのスマホでは、棋譜ツリー・形勢グラフ・品質表はドロワーではなく盤の横の常設カラムに表示され、外縁（三列のときはカード間）をドラッグして幅を変えられます。

### 座席

対戦相手は色ごとに別々に選びます。だから、新規対局シートが「対人対局」と「人 vs AI」しか用意していなくても、AI 同士の組み合わせが可能なのです。4 種類の座席は次のとおりです。

- **人間** —— この色は同じ端末の人間が打ちます。
- **段位 AI** —— エンジンに 1 回訪問の policy を求め、座席は選択した棋力に合わせて KaTrain が較正した式で、その policy から一手を引きます。局地の戦いは素早い一方で、その棋力の人間らしい弱点も持ちます。
- **人間らしい AI** —— 同じ 1 回訪問クエリを使いますが、エンジンには加えて人間ネットワークを `humanSLProfile`（例: `preaz_5k`）で要求します。そして、その人間 policy から着手をサンプリングするので、弱めに調整されたエンジンというより、選んだ棋力の人間のように打ちます。
- **KataGo 9D+** —— 設定した play visits の予算内で、エンジンが最善と判断した手を打ちます。

段位 AI と人間らしい AI はどちらも 15k〜3d（15 級〜3 段）の間で棋力を選べます（デフォルトは 5 級）。対局中でもサイドパネルから座席を変更できます。ドロワーを開くと AI は一時停止するので、盤が動き続ける心配をせずに変更を検討できます。

### 検討と解析

打ち終わった対局を見直すのがもうひとつの主な用途で、それは棋譜ツリーの上に直接作られています。最新の着手より前まで Undo すると、あなたは検討中です。現在のノードに子がある——それがこのアプリで「検討中」が意味するところです。そうした途中のノードでは次の手は人間のもので、石を置けばそこから変化が分岐します。Redo は好みのラインを前方に進み、エンジンはツリーの葉、それも自分の色の番にしか動きません。これにより、調べているラインに AI の着手が割り込むことは絶対にありません。

グラフと品質表に表示される評価は、手ごとに収集されます。だからこそ、これらの機能はエンジンが接続されて初めて現れます。現在の局面には、変化（PV）・損失目数・訪問数付きの候補手が表示され、**Analyze game** は好みのライン全体をバックグラウンドで検討し、各ノードに順番に完全な解析を要求します。検討中の局面では、合法点を長押しまたは右クリックすると、エンジンが双方の最善進行（最大 16 手）を手数つきの仮想石として示します。棋譜ツリーに新しい変化は作られず、領地のヒートは仮想石が落ちるたびに追従します。

### 保存と記録

保存はドロワーから行います。**Save** は現在の記録を更新し、**Save as** は新しい名前でコピーを保存します。どちらも対局を手ごとの評価とともに最近のリストへ書き込むため、再起動後も形勢カーブと品質集計が戻ってきます。アプリは最後の保存から局面が変わったかを追跡しているので、未保存の手を残したまま対局画面を抜けようとすると、保存・破棄・キャンセルを選ぶダイアログが出ます。SGF ファイルの読み込みと書き出しにも対応しており、形式は FF[4] です。これはほとんどの囲碁ツールが使う交換形式です。**Copy SGF** は現在の棋譜をファイルダイアログなしでシステムクリップボードへコピーします。

## 外観としきい値

外観テーマと解析のしきい値は、どちらも設定画面で構成します。石と外観の組み合わせは 4 つあり、それぞれが 2 つの座席の色——つまり勝率バーとカーブの色も——を定義します。

- **Sky & Sakura** —— 快晴の空色と桜（デフォルト）
- **Ink & Paper** —— 深い藍と桜和紙
- **Midnight & Snow** —— 夜のチャコールと温かな雪
- **Lilac & Peach** —— 柔らかなライラックと熟した桃

勝率バーは 2 色の石の色で塗られ、境界が現在の勝率の割合を示します。最終着手のリングは、いま置かれた石の色を取ります。主な機能の節で触れた品質しきい値も同じページで編集でき、領地スタイルのピッカーがすぐ隣にあります。等級づけと外観が 1 か所にまとまっているわけです。

## エンジンとゲートウェイ

この節では、エンジンの接続方法と、リポジトリに同梱されている小さなゲートウェイの仕組みを説明します。エンジン設定画面には接続プロファイル（`;` 区切りで複数指定できる WebSocket URL、任意のトークン、play 用と review 用に分かれた訪問数予算）と、接続テストとベンチマークの実行操作があります。複数あるときは先頭から試し、最初に応答したものを使います。ベンチマークはまず `query_version` でネットワーク往復を測り、続けて 1 回訪問の overlay クエリ、80・400・2000 訪問の探索ラダー、人間ネットワークのプローブを測定します。判定はネットワーク遅延とハードウェアを分け、ハードウェアは RTT を除いた visits/s を 0〜100 の連続バーに載せます。遠い回線上の速い GPU と、localhost 上の弱い CPU が同じ評価に落ちることはありません。所要時間はおよそ 15〜70 秒です。

エンジンの通信はすべて、WebSocket 上の KataGo Analysis JSON です。つまり、同期を保つべき第二のプロトコルはありません。クエリは `rootInfo`・`moveInfos`・`ownership`・`policy`、必要なら `humanPolicy` を要求します。勝率は黒番基準で保存・報告されます。人間らしい AI と段位 AI は、1 回訪問で policy を要求するクエリを使います。一手を引き出すためだけに policy があれば十分だからです。人間らしい AI は同じクエリで `humanSLProfile`（例: `preaz_5k`）も送ります。ライブ解析と KataGo 9D+ の着手は play visits 予算を使い、キューに入れた **Analyze game** の検討は review visits 予算を使います。

<p align="center">
  <img src="screenshots/engine.jpg" alt="エンジン設定——WebSocket URL、play visits、review visits、接続テスト"/>
</p>

エンジンがオフラインの間、エンジンに依存する UI（グラフ、品質マーク、領地オーバーレイ、AI の着手）は何もしないか空のままになり、対人対局はこれまでどおり機能します。

### 同梱のゲートウェイ

エンジンクライアントが `ws://127.0.0.1:2080` のようなアドレスを想定しているため、リポジトリにはその URL をそのまま提供する小さな Python ゲートウェイが含まれています。このアドレスはあくまでデフォルトです。ゲートウェイは自分が管理するどのマシンでも起動でき、アプリのエンジン設定で別のアドレス（たとえばスマホからデスクトップ PC の LAN IP）を指すこともできます。プロジェクトルートから:

```bash
pip install -r engine/requirements.txt
python engine/server.py --katago /path/to/katago
```

`requirements.txt` の依存は `websockets` だけです。初回起動時、ゲートウェイは `model/` ディレクトリがなければ作成し、KataGo の GitHub releases から 2 つのネットワークをダウンロードします。メインネットワークの `b10c384h6nbttflrs` と、人間らしい AI の座席が必要とする人間SLネットワークの `b18c384nbt-humanv0` です。ファイルを自分で置いてあるなら、`--skip-download` でダウンロードを省略できます。エンジンの調整パラメータは `engine/analysis.cfg` にあり、KataGo のキャッシュとログは `engine/home/` に置かれます。KataGo のバイナリ自体は GPU 依存のためダウンロードされません。ゲートウェイは、`--katago` で渡されたパス、`engine/bin/katago`、`PATH` 上の `katago` 実行ファイルの順に探します。

## ビルドと実行

デスクトップアプリは、リポジトリから直接起動できます。

```bash
./gradlew :desktopApp:run
# 開発中のホットリロード
./gradlew :desktopApp:hotRun --auto
```

エンジンを用意するなら、アプリを起動する前に上の節のゲートウェイを実行します（初回起動でネットワークは `model/` に置かれます）。

```bash
pip install -r engine/requirements.txt
python engine/server.py --katago /path/to/katago
```

iOS では Xcode で [`iosApp/`](./iosApp) を開いてください。注意が 1 つあります。SGF の開く/書き出しダイアログはデスクトップと Android に実装されているため、この 2 つの操作は現在 iOS シェルでは何も起こりません。

### ターミナルから Android を

Android アプリは `:androidApp` モジュール（`applicationId` は `com.acite.katahana`）。Gradle に Android SDK の場所を教える必要があり、それは `local.properties` に書きます。

```
sdk.dir=/path/to/Android/Sdk
```

`adb` は `$sdk.dir/platform-tools/adb` にあります（またはすでに `PATH` に載っています）。

**実機へ。** USB デバッグを有効にした端末をつなぎ、RSA のプロンプトを承認します。

```bash
adb devices
```

表示されるのは `device` であるべきで、`unauthorized` や `offline` ではありません。複数の端末を同時に使っていますか？ `adb devices -l` でシリアルを確認し、すべての `adb` コマンドに `-s <serial>` を付けるか、`ANDROID_SERIAL=<serial>` をエクスポートして、Gradle にも同じ端末を選ばせてください。

**ワイヤレス**（Android 11+ の開発者オプション → ワイヤレスデバッグ）:

```bash
adb pair <ip>:<pairing-port>
adb connect <ip>:<debug-port>
adb devices
```

**端末へ Release を。** Gradle が release APK をビルドして署名し、あとは adb が起動まで行います。

```bash
./gradlew :androidApp:installRelease
adb shell am start -n com.acite.katahana/.MainActivity
```

同じインストールでも、APK ファイルを手元に残したい場合:

```bash
./gradlew :androidApp:assembleRelease
adb install -r androidApp/build/outputs/apk/release/androidApp-release.apk
```

`-r` は既存の KataHana を置き換えます。adb が `INSTALL_FAILED_UPDATE_INCOMPATIBLE` と返したら、端末に残っているコピーは別の鍵で署名されています——先にアンインストールして、もう一度試してください。

```bash
adb uninstall com.acite.katahana
adb install androidApp/build/outputs/apk/release/androidApp-release.apk
```

**APK だけ欲しい**（端末不要）:

```bash
./gradlew :androidApp:assembleRelease
# androidApp/build/outputs/apk/release/androidApp-release.apk
```

Play 式の App Bundle がお好みなら:

```bash
./gradlew :androidApp:bundleRelease
# androidApp/build/outputs/bundle/release/androidApp-release.aab
```

署名についての覚え書き：現在の release ビルドは **debug** キーストアで署名し（`androidApp/build.gradle.kts` の `signingConfig = signingConfigs.getByName("debug")`）、縮小化もオフのままです。だから `installRelease` が自分のキーストアなしで通るのです——それでも本物の release バリアントです（`debuggable=false`）。Play へのアップロードでは、後日あらためて署名設定が要るでしょう。

**Debug**（IDE の実行構成がふつうインストールするもの）:

```bash
./gradlew :androidApp:installDebug
# または
./gradlew :androidApp:assembleDebug
# androidApp/build/outputs/apk/debug/androidApp-debug.apk
```

## コード構成

このプロジェクトは Kotlin Multiplatform 構成で、Gradle モジュールは 3 つです。`shared` がゲームロジックと Compose UI を持ち、`androidApp` と `desktopApp` は薄いランチャーです。`iosApp/` の iOS アプリは同じ共有 UI を包みます。`shared` のうち、OS に依存しないものはすべて `commonMain` に置かれ、`jvmMain`・`androidMain`・`iosMain` は、ファイルアクセス・設定のパス・HTTP/WebSocket クライアントエンジン・画面ライフサイクルのフックといった、各プラットフォームが必ず提供する部品だけを供給します。

エンジンクライアントは、`engine/` パッケージにある薄い WebSocket 接続です。ホーム画面のバージョン表記と更新ログはハードコードされていません。`shared/build.gradle.kts` の Gradle タスクがビルド時にいくつかの `git` コマンドを実行し、UI が読む小さな Kotlin ファイルを生成します。ナビゲーションは Voyager、依存性注入は Metro、設定の保存は DataStore です。

```
shared/src/commonMain/kotlin/com/acite/katahana/
  domain/     棋譜ツリー・ルール・連絡・評価系列
  engine/     WebSocket クライアント・Analysis JSON・領地
  ai/         HumanBot・RankBot・FullStrengthBot・品質帯
  settings/   設定と領地スタイル
  recents/    Save / Save as の棚・保存された評価
  changelog/  git タグをホームのログへ
  sgf/        SGF 読み書き
  ui/         盤・対局・ホーム・テーマ
```
